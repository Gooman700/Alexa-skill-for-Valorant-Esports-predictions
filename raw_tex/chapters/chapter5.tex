\section{Project Architecture}
The design of the VCT match predictor follows a modular, event-driven architecture. This methodology was selected to ensure a strict separation of concerns between the VUI and the underlying machine learning logic. By decoupling the presentation layer (Alexa Skill) from the processing layer (AWS Lambda), the system becomes highly maintainable; for instance, the machine learning model can be retrained and redeployed without necessitating changes to the front-end interaction model.

This approach is further justified by the serverless nature of the deployment environment. An event-driven design aligns with the execution patterns of AWS Lambda, where the system only consumes computational resources in response to a specific user request. This ensures high scalability and cost-efficiency while meeting the low-latency requirements established in \autoref{chap:req_analysis}. To facilitate this modularity, the system will be structured into a three-layer architecture.

The presentation layer is responsible for the interaction model, including automatic speech recognition and natural langage understanding. It will capture user utterances and resolve them into structured JSON payloads (intents and slots) to be passed to the logic layer. The logic layer will host the Python backend. It will be responsible for dialogue management, slot validation, and invoking the machine learning prediction algorithm. The data layer will house the static assets required for prediction, including the serialised machine learning model and the pre-calculated rolling statistics database. By isolating the data from the logic, the system ensures that the feature set can be updated independently of the application code.

\section{Alexa Voice User Interface}
The VUI will be designed to serve as the primary point of interaction, translating natural language into structured data. The design will follow an approach where the interface is modelled as a conversation rather than a series of menus. This is essential for maintaining the conversational tone established in the non-functional requirements \autoref{tab:non_functional_req}.

\subsection{Prediction Intent and Utterances}
The core functionality of the skill will be encapsulated within an intent called `PredictMatchIntent'. This intent will be designed to handle the primary user goal: obtaining a match outcome prediction. To fulfil this request, the intent will rely on two mandatory \glspl{slot}: team\_a and team\_b. Many sample utterances will be attached to this intent, such as ``Who is going to win between \{team\_a\} and \{team\_b\}?''. \autoref{tab:utterances} contains a comprehensive list of sample utterances. Both slots will pull from a complete list of slot values---stored in a slot type `teams'---which will consist of every team name present in the dataset. When the user invokes the skill and triggers the `PredictMatchIntent', Alexa Voice Services (AVS) will utilise its Natural Language Understanding (NLU) engine to perform entity resolution on the user's speech.

AVS will attempt to map the spoken team names to the canonical values defined in the `teams' slot type. In scenarios where the audio input is phonetically ambiguous, AVS will resolve the speech to multiple potential matches, which will be delivered to the AWS Lambda function as a collection of resolutions ordered by confidence scoring. The backend logic will be designed to evaluate these resolutions, prioritising the high-confidence match while maintaining the ability to trigger a disambiguation prompt if the resolution is below a specific certainty threshold. This ensures that even with slight mispronunciations, the intent will still receive the correct team identifiers required for the machine learning inference.

\subsection{Dialog Management}
The interaction model will be configured to mark both `team\_a' and `team\_b' as required, allowing for manual delegation to be enabled within the backend logic. Automatic Alexa-led delegation is an available configuration; however, the design for this project will employ manual delegation. While automatic delegation simplifies the interaction model, it offers limited control over the specific linguistic prompts and error-handling logic. By implementing a manual strategy, the backend logic can evaluate the state of the slots at each turn of the conversation. If the model detects that a team name provided by the user is phonetically valid but missing from the training dataset, a custom prompt will be triggered using the \texttt{ElicitSlotDirective}. This level of granularity is not possible with automatic delegation, making the manual approach essential for fulfilling the project's requirement to provide context-aware, meaningful error messages and ensure a fluid user experience.

In instances where a user provides an incomplete utterance, the system will enter a ``re-prompt" state to resolve the missing information. This will be programmatically managed via the \texttt{add\_\allowbreak directive} method of the ASK SDK, which facilitates the queuing of specific response instructions. Specifically, the system will be designed to instantiate and pass an \texttt{ElicitSlot\allowbreak Directive} object to this method. This directive will explicitly instruct the Alexa service to prompt the user for the specific missing slot (e.g., ``I didn't hear the second team. Which team is Fnatic playing against?''). To ensure a fluid conversational experience, the system will utilise the \texttt{Session\allowbreak Attributes} and \texttt{IntentRequest} objects to maintain state. This architecture ensures that previously gathered information is persisted in the session context, preventing the loss of the first team's identity while the second is being elicited. Consequently, the final prediction logic will only be triggered once a complete and validated set of slot values is present in the request envelope.

\section{Data Transformation}
The design of the machine learning algorithm will rely on a data derivation pipeline that transforms raw \gls{vct} statistics into high-level predictive features. Because professional Valorant performance is evolutionary and subject to meta-shifts, raw match figures are insufficient when used in isolation. Due to frequent balancing updates around agent abilities and map layouts, statistics pertaining to matches played in previous updates hold less predictive power when compared to new match data. Instead, the system will be designed to derive features that represent a team's current ``form'' and relative competitive strength.

\subsection{Feature Derivation}
The feature transformation pipeline is designed to convert static match results into a dynamic representation of competitive momentum. To capture these temporal trends, the system will implement a rolling average strategy where raw performance metrics are aggregated over a sliding window of the previous 15 matches. This specific window size is selected to ensure the model prioritises recent strategic shifts and consistency while maintaining a large enough sample size to mitigate the influence of stochastic anomalies. The implementation will utilise the \texttt{pandas} library to orchestrate these complex transformations, leveraging indexed relational joins to align historical performance with upcoming match fixtures.

Central to this pre-implementation design is the derivation of the \texttt{Roll\_Form} variable, which serves as a weighted measure of a team's recent success across all maps. This will be calculated by grouping the dataset by \texttt{team\_id} and applying the \texttt{.rolling()}---with a `window' parameter of 15---and \texttt{.mean()} functions to a binary win/loss column. To ensure the rolling average only accounts for chronological history, the \texttt{.shift(1)} method will be applied; this prevents data leakage by ensuring the current match result is not included in its own predictive feature. This is complemented by the \texttt{Roll\_Map} feature, a map-specific rolling average that accounts for the fact that professional teams often exhibit significant variance in performance across different environments. This calculation requires a secondary grouping level, using \texttt{.groupby()} with a list containing the `team\_id' and `map' labels passed in, allowing the system to isolate a team's proficiency on a specific map. The resulting series will then be merged back into the primary dataframe using a left join on the match and team identifiers.

To further refine the model's understanding of dominance, the system will derive the \texttt{Roll\_RD} (Rolling Round Differential) feature. This metric provides a higher fidelity of information than a simple win-loss binary, as it allows a logical distinction of teams that won a match by one round, and teams that won a match by 13 rounds, one of which clearly showing superior ability. Furthermore, the design incorporates a \texttt{H2H\_Win\_Diff} (Head-to-Head Win Differential) variable to account for specific playstyle mismatches or psychological advantages between two specific teams. This is particularly vital in professional \gls{vct} play where certain teams may prove much stronger depending on their opponent. 

Finally, the environmental context of the match will be handled through the processing of the 12 \texttt{Map\_name} categorical features (one for each map). Using one-hot encoding, the system will allow the supervised learning algorithms to learn map-specific biases and weightings. By combining these rolling performance indicators with categorical map data, the design ensures that the model evaluates the competition not just on who the teams are, but on how they are currently performing within the specific tactical constraints of the chosen map. This comprehensive data transformation process is essential for meeting the established accuracy thresholds, as it effectively collapses multidimensional historical data into a singular, high-utility input vector for the ML model. \autoref{tab:feature_summary} contains a summary of the proposed features and their justification to predictive utility.

\subsection{Dimensionality Reduction}
A critical design challenge is the selection of a feature subset that maximises predictive power while minimising redundancy. Including multiple features that explain the same underlying relationship---such as total eliminations and damage dealt---can introduce multicollinearity. This state can lead to an overfit model that is overly sensitive to noise and fails to generalise to unseen match data.

The design will involve a **Feature Weighting Review** during the preliminary training phase. The following methods will be implemented to refine the feature set:
\begin{itemize}
    \item \textbf{Correlation Analysis:} A correlation matrix will be generated to identify features with high internal coefficients. Where two features provide redundant information, the design specifies that only the feature with the highest correlation to the target variable (the match winner) will be retained.
    \item \textbf{Differential Calculation:} The model will be designed to process ``Differential Features.'' By calculating the delta between Team A and Team B metrics (e.g., $Team\_A\_ACS - Team\_B\_ACS$), the system collapses two absolute values into a single relative metric. This design choice is justified as it directly quantifies the competitive gap between the two organisations, which serves as a more potent predictor than isolated statistics.
\end{itemize}

\subsection{Feature Persistence and Latency Optimization}
To satisfy the non-functional requirement for low-latency responses, these derived features will be stored in a pre-calculated **Feature Store**. The design dictates that the Logic Tier will not perform these heavy derivations in real-time during an Alexa session. Instead, the lambda function will use the resolved team \glspl{slot} to perform a high-speed lookup in a pre-processed table. This trade-off ensures that complex statistical analysis is performed offline, allowing the inference engine to deliver predictions within the specified six-second window.
