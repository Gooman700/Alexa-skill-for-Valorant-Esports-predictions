\chapter{Design}
The design of the VCT match predictor follows a modular, event-driven architecture. This methodology was selected to ensure a strict separation of concerns between the VUI and the underlying machine learning logic. By decoupling the presentation layer (Alexa Skill) from the processing layer (AWS Lambda), the system becomes highly maintainable; for instance, the machine learning model can be retrained and redeployed without necessitating changes to the front-end interaction model.

This approach is further justified by the serverless nature of the deployment environment. An event-driven design aligns with the execution patterns of AWS Lambda, where the system only consumes computational resources in response to a specific user request. This ensures high scalability and cost-efficiency while meeting the low-latency requirements established in \autoref{chap:req_analysis}. To facilitate this modularity, the system will be structured into a three-layer architecture.

The presentation layer is responsible for the interaction model, including automatic speech recognition and natural language understanding. It will capture user utterances and resolve them into structured JSON payloads (intents and slots) to be passed to the logic layer. The logic layer will host the Python backend. It will be responsible for dialogue management, slot validation, and invoking the machine learning prediction algorithm. The data layer will house the static assets required for prediction, including the serialised machine learning model and the pre-calculated rolling statistics database. By isolating the data from the logic, the system ensures that the feature set can be updated independently of the application code.

\section{Alexa Voice User Interface}
The VUI will be designed to serve as the primary point of interaction, translating natural language into structured data. The design will follow an approach where the interface is modelled as a conversation rather than a series of menus. This is essential for maintaining the conversational tone established in the non-functional requirements \autoref{tab:non_functional_req}.

\subsection{Prediction Intent and Utterances}
The core functionality of the skill will be encapsulated within an intent called \texttt{PredictMatchI\-ntent}. This intent will be designed to handle the primary user goal: obtaining a match outcome prediction. To fulfil this request, the intent will rely on two mandatory \glspl{slot}: team\_a and team\_b. Many sample utterances will be attached to this intent, such as ``Who is going to win between \{team\_a\} and \{team\_b\}?''. \autoref{tab:utterances} contains a comprehensive list of sample utterances. Both slots will pull from a complete list of slot values---stored in a slot type `teams'---which will consist of every team name present in the dataset. When the user invokes the skill and triggers the \texttt{PredictMatchIntent}, Alexa Voice Services (AVS) will utilise its Natural Language Understanding (NLU) engine to perform entity resolution on the user's speech.

AVS will attempt to map the spoken team names to the canonical values defined in the `teams' slot type. In scenarios where the audio input is phonetically ambiguous, AVS will resolve the speech to multiple potential matches, which will be delivered to the AWS Lambda function as a collection of resolutions ordered by confidence scoring. The backend logic will be designed to evaluate these resolutions, prioritising the high-confidence match while maintaining the ability to trigger a disambiguation prompt if the resolution is below a specific certainty threshold. This ensures that even with slight mispronunciations, the intent will still receive the correct team identifiers required for the machine learning inference.

Additionally, an intent \texttt{FetchStatHistoryIntent} could facilitate the necessary procedures to provide the user with quantitative historical data about statistics and teams of their interest. The essential slots for this intent are \texttt{team}, \texttt{stat}, \texttt{match\_count}, and \texttt{time\_period}. \autoref{tab:HistoryIntentSlots} below outlines the utility reason for including each slot, as well as an example of each.

\subsection{Dialogue Management}
\label{sub:dialogManagement}
As a result of the identified mitigation strategies, the interaction model will be configured to mark both `team\_a' and `team\_b' as required, allowing for manual delegation to be enabled within the backend logic. This will provide a concrete approach to implement the turn-based logic as required by the designed mitigations. While automatic delegation simplifies the interaction model, it offers limited control over the specific linguistic prompts and error-handling logic. By implementing a manual strategy, the backend logic can evaluate the state of the slots at each turn of the conversation. If the model detects that a team name provided by the user is phonetically valid but missing from the training dataset, a custom prompt will be triggered using the \texttt{ElicitSlotDirective}. This level of granularity is not possible with automatic delegation, making the manual approach essential for fulfilling the project's requirement to provide context-aware, meaningful error messages and ensure a fluid user experience.

In instances where a user provides an incomplete utterance, the system will enter a ``re-prompt'' state, as outlined in \autoref{tab:EdgeCaseHandling}, to resolve the missing information. This will be programmatically managed via the \texttt{add\_\-directive} method of the ASK SDK, which facilitates the queuing of specific response instructions. Specifically, the system will be designed to instantiate and pass an \texttt{ElicitSlot\-Directive} object to this method. This directive will explicitly instruct the Alexa service to prompt the user for the specific missing slot (e.g., ``I didn't hear the second team. Which team is Fnatic playing against?''). To ensure a fluid conversational experience, the system will utilise the \texttt{Session\-Attributes} and \texttt{IntentRequest} objects to maintain state. This architecture ensures that previously gathered information is persisted in the session context, preventing the loss of the first team's identity while the second is being elicited. Consequently, the final prediction logic will only be triggered once a complete and validated set of slot values is present in the request envelope.

\section{Data Transformation}
The design of the machine learning algorithm will rely on a data derivation pipeline that transforms raw \gls{vct} statistics into high-level predictive features. Because professional Valorant performance is evolutionary and subject to meta-shifts, raw match figures are insufficient when used in isolation. Due to frequent balancing updates around agent abilities and map layouts, statistics pertaining to matches played in previous updates hold less predictive power when compared to new match data. Instead, the system will be designed to derive features that represent a team's current ``form'' and relative competitive strength.

\subsection{Feature Derivation}
The feature transformation pipeline is designed to convert static match results into a dynamic representation of competitive momentum. To capture these temporal trends, the system will implement a rolling average strategy where raw performance metrics are aggregated over a sliding window of the previous 15 matches. This specific window size is selected to ensure the model prioritises recent strategic shifts and consistency while maintaining a large enough sample size to mitigate the influence of stochastic anomalies. The implementation will utilise the \texttt{pandas} library to orchestrate these complex transformations, leveraging indexed relational joins to align historical performance with upcoming match fixtures.

Central to this pre-implementation design is the derivation of the \texttt{Roll\_Form} variable, which serves as a weighted measure of a team's recent success across all maps. This will be calculated by grouping the dataset by \texttt{team\_id} and applying the \texttt{.rolling()}---with a `window' parameter of 15---and \texttt{.mean()} functions to a binary win/loss column. To ensure the rolling average only accounts for chronological history, the \texttt{.shift(1)} method will be applied; this prevents data leakage by ensuring the current match result is not included in its own predictive feature. This is complemented by the \texttt{Roll\_Map} feature, a map-specific rolling average that accounts for the fact that professional teams often exhibit significant variance in performance across different environments. This calculation requires a secondary grouping level, using \texttt{.groupby()} with a list containing the `team\_id' and `map' labels passed in, allowing the system to isolate a team's proficiency on a specific map. The resulting series will then be merged back into the primary dataframe using a left join on the match and team identifiers.

To further refine the model's understanding of dominance, the system will derive the \texttt{Roll\_RD} (Rolling Round Differential) feature. This metric provides a higher fidelity of information than a simple win-loss binary, as it allows a logical distinction of teams that won a match by one round, and teams that won a match by 13 rounds, one of which clearly showing superior ability. Furthermore, the design incorporates a \texttt{H2H\_Win\_Diff} (Head-to-Head Win Differential) variable to account for specific playstyle mismatches or psychological advantages between two specific teams. This is particularly vital in professional \gls{vct} play where certain teams may prove much stronger depending on their opponent. 

Finally, the environmental context of the match will be handled through the processing of the 12 \texttt{Map\_name} categorical features (one for each map). Using one-hot encoding, the system will allow the supervised learning algorithms to learn map-specific biases and weightings. By combining these rolling performance indicators with categorical map data, the design ensures that the model evaluates the competition not just on who the teams are, but on how they are currently performing within the specific tactical constraints of the chosen map. This comprehensive data transformation process is essential for meeting the established accuracy thresholds, as it effectively collapses multidimensional historical data into a singular, high-utility input vector for the ML model. \autoref{tab:feature_summary} contains a summary of the proposed features and their justification to predictive utility.

\subsection{Dimensionality Reduction}
After the aforementioned features have been derived, the dataset must be checked for multicollinearity. Failure to do so could result in multiple independent variables being highly correlated, wasting the computational resources available. This state can lead to an overfit model that is overly sensitive to noise and fails to generalise to unseen match data.

The design involves a feature weighting review during the preliminary training phase. The model will be designed to process differential features. By calculating the delta between Team A and Team B metrics (e.g., $Team\_A\_Score - Team\_B\_Score$), the system collapses two absolute values into a single relative metric. This directly quantifies the competitive gap between the two teams, which serves as a more potent predictor than isolated statistics. Additionally, a correlation matrix will be generated to identify features with high internal coefficients. Where two features provide redundant information, only the feature with the highest correlation to the target variable (the match winner) will be retained.

\subsection{Team-Specific Feature Storage}
\label{sub:featureStorage}
To satisfy the latency requirements defined in \autoref{chap:req_analysis}, the system will utilise a pre-calculated feature store for team-specific metrics. For each independent data point required to calculate differential features---such as \texttt{Roll\_Form} or \texttt{Roll\_RD}---the most recent rolling average value will be persisted within a structured CSV file. This file will include a \texttt{Team\_ID} column to serve as a primary key, facilitating efficient relational mapping between the Alexa slot values and the historical dataset.

Furthermore, to facilitate the functionality required for the \texttt{FetchStatHistoryIntent} to be implemented, a history of match-specific data needs to be persisted within another CSV file. This historical data store will contain a simplified collection of features essential for trivial filtering. The \texttt{pandas} library will enable results to be produced fast, and with ease.

This design enables an offline, local cache of the most up-to-date features to be bundled within the AWS Lambda environment. By hosting the feature store locally within the execution context, the system eliminates the significant latency that would otherwise arise from on-the-fly calculations or remote database queries. Instead, the Lambda function will use the resolved team \glspl{slot} to perform a high-speed lookup in the pre-processed table. This architectural choice ensures that match predictions are delivered within the six-second window specified in the non-functional requirements.

\section{Machine Learning Model Design}
The predictive core of the system will be designed using a supervised learning approach, focusing on binary classification to determine the most likely match winner. To ensure a high predictive accuracy, the design incorporates both a baseline statistical model and a more complex ensemble algorithm.

\subsection{Algorithm Selection}
Logistic Regression will be implemented as the primary baseline model. While Logistic Regression is a linear classifier and may struggle with the complex, non-linear relationships often present in esports data, its inclusion is justified as a performance benchmark. As noted in the analysis of similar predictive systems, Logistic Regression offers high interpretability and extremely low computational overhead, making it an ideal control against which the performance of more complex models can be measured.

To capture the non-linear interactions between features, the system will utilise gradient boosted trees. This method is strong against outliers and capable of performing internal feature selection, which could prove helpful for handling the inherent noise within esports data. The Scikit-Learn library will be used for model implementation due to its comprehensive suite of ML algorithms and evaluation tools.

\subsection{Training Strategy}
The model's hyper-parameters, specifically for the gradient boosted model---including learning\_r\-ate, n\_estimators, and max\_depth---will be methodically stepped until an optimal value is reached. This will ensure that accuracy is not lost due to sub-optimal hyper-parameter values. One hyper-parameter will be refined at a time, until all are optimised. During training, the individual feature weights given by the model can be examined to inform future design changes for the feature set. Existing features can be discarded, and new features can be introduced, negating the impact of multicollinearity and improving the explained variance coverage.

\subsection{Model Serialisation}
To integrate the trained model into the logic layer, the final model will be serialised using the \texttt{joblib} library. This process converts the trained Python object into a persistent \texttt{.joblib} file format. This file will be packaged within the AWS Lambda deployment, allowing the Lambda Function to load the model into memory instantly upon invocation, bypassing the need for a training phase during the user's request.

\section{Lambda Function Design}
The AWS Lambda Function serves as the integration point between the \gls{vui} and the machine learning model. The internal logic of the function will be designed using a handler pattern---as expected of the Alexa Skills Kit (\gls{ask})---to ensure clean routing of requests.

\subsection{Handler Design Pattern}
As part of this design, a handler class will be implemented for each high-level intent, providing an entry point to execute the logic designed to fulfil the request. Every request handler will extend \texttt{AbstractRequestHandler}, a class provided by Amazon's \gls{ask}-\gls{sdk}, and implement two methods provided by it: \texttt{can\_handle} and \texttt{handle}. The \texttt{can\_handle} method returns a Boolean value indicating if the request handler can create an appropriate response for the request. Acquired from the JSON object generated from the user's speech, the \texttt{can\_handle} method has access to the request type and additional attributes that the skill may have set in previous requests or even saved from a previous interaction. The request type can be utilised to determine if the handler is appropriate to process the JSON object, or if the request is designed to be processed by another handler. 

Upon receiving the JSON request from Alexa Voice Services (\gls{avs}), the Lambda Function will cascade through each handler class and call the \texttt{can\_handle} method. A handler will return True if the conditions programmed are met, or False if not. In the case of conditions not being met, the JSON will continue to be passed down methodically to other handlers, one by one in the specific order that they are declared. Conversely, if the conditions within a handler's \texttt{can\_handle} method are met, True is returned, and the JSON will cease to be cascaded. Consequently, the \texttt{handle} method belonging to the same handler, designed to execute the logic required to satisfy the user's request, will be executed. \subsection{Handler Pattern Implementation}
For both the \texttt{PredictMatchIntentHandler} and \texttt{FetchStatHistoryIntentHandl\-e\-r}, the \texttt{can\_handle} method will return True when the request type of the JSON object matches ``\texttt{PredictMatchIntent}'' and ``\texttt{FetchStatHistoryIntent}'' respectively. The request type of a handler request will be extracted via execution of the \texttt{ask\_utils.is\_request\_ty\-p\-e} method.

Upon the \texttt{handle} method of the \texttt{PredictMatchIntentHandler} class being called, any present edge cases as established in \autoref{tab:EdgeCaseHandling} will be identified and consequently resolved within the handler through the methods explained in \autoref{sub:dialogManagement}. Once the request is validated, the statistics required for use as features in the ML model will be retrieved from the feature store detailed in \autoref{sub:featureStorage}, formatted into a list, and within the serialised model as parameters, to produce a prediction. Similarly, the \texttt{FetchStatHistoryIntentHandler} will firstly resolve erroneous requests, before executing a custom query upon the historical data store. The query result will be prosified and spoken back to the user.
