\chapter{Design}
The design of the VCT match predictor follows a modular, event-driven architecture. This methodology was selected to ensure a strict separation of concerns between the VUI and the underlying machine learning logic. By decoupling the presentation layer (Alexa Skill) from the processing layer (AWS Lambda), the system becomes highly maintainable; for instance, the machine learning model can be retrained and redeployed without necessitating changes to the front-end interaction model.

This approach is further justified by the serverless nature of the deployment environment. An event-driven design aligns with the execution patterns of AWS Lambda, where the system only consumes computational resources in response to a specific user request. This ensures high scalability and cost-efficiency while meeting the low-latency requirements established in \autoref{chap:req_analysis}.

\section{Alexa Voice User Interface}
The VUI will be designed to serve as the primary point of interaction, translating natural language into structured data. The design will follow an approach where the interface is modelled as a conversation rather than a series of menus. This is essential for maintaining the conversational tone established in the non-functional requirements \autoref{tab:non_functional_req}.

\subsection{Prediction Intent and Utterances}
The core functionality of the skill will be encapsulated within an intent called `PredictMatchIntent'. This intent will be designed to handle the primary user goal: obtaining a match outcome prediction. To fulfil this request, the intent will rely on two mandatory \glspl{slot}: team\_a and team\_b. Many sample utterances will be attached to this intent, such as ``Who is going to win between \{team\_a\} and \{team\_b\}?''. Both slots will pull from a comprehensive list of slot values---stored in a slot type `teams'---which will consist of every team name present in the dataset. When the user invokes the skill and triggers the `PredictMatchIntent', Alexa Voice Services (AVS) will utilise its Natural Language Understanding (NLU) engine to perform entity resolution on the user's speech.

AVS will attempt to map the spoken team names to the canonical values defined in the `teams' slot type. In scenarios where the audio input is phonetically ambiguous, AVS will resolve the speech to multiple potential matches, which will be delivered to the AWS Lambda function as a collection of resolutions ordered by confidence scoring. The backend logic will be designed to evaluate these resolutions, prioritising the high-confidence match while maintaining the ability to trigger a disambiguation prompt if the resolution is below a specific certainty threshold. This ensures that even with slight mispronunciations, the intent will still receive the correct team identifiers required for the machine learning inference.

\subsection{Dialog Management}
The interaction model will be configured to mark both team\_a and team\_b as required, allowing for manual delegation to be enabled within the backend logic. Automatic Alexa-led delegation is an available configuration; however, the design for this project will employ manual delegation. While automatic delegation simplifies the interaction model, it offers limited control over the specific linguistic prompts and error-handling logic. By implementing a manual strategy, the backend logic can evaluate the state of the slots at each turn of the conversation. If the model detects that a team name provided by the user is phonetically valid but missing from the training dataset, a custom prompt will be triggered using the \texttt{ElicitSlotDirective}. This level of granularity is not possible with automatic delegation, making the manual approach essential for fulfilling the project's requirement to provide context-aware, meaningful error messages and ensure a robust user experience.

In instances where a user provides an incomplete utterance, the system will enter a ``re-prompt" state to resolve the missing information. This will be programmatically managed via the \texttt{add\_\allowbreak directive} method of the ASK SDK, which facilitates the queuing of specific response instructions. Specifically, the system will be designed to instantiate and pass an \texttt{ElicitSlot\allowbreak Directive} object to this method. This directive will explicitly instruct the Alexa service to prompt the user for the specific missing slot (e.g., ``I didn't hear the second team. Which team is Fnatic playing against?''). To ensure a fluid conversational experience, the system will utilise the \texttt{Session Attributes} and \texttt{IntentRequest} objects to maintain state. This architecture ensures that previously gathered information is persisted in the session context, preventing the loss of the first team's identity while the second is being elicited. Consequently, the final prediction logic will only be triggered once a complete and validated set of slot values is present in the request envelope.
