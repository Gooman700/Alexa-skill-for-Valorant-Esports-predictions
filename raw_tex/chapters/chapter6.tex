\chapter{Implementation and testing}
This chapter details the implementation of the system, documenting the rationale behind design deviations and the technical constraints that necessitated them. Furthermore, it outlines the testing procedures employed to validate system performance. The implementation was developed using Python 3.14, leveraging a stack of libraries including \texttt{NumPy}, \texttt{scikit-learn}, \texttt{pandas}, and \texttt{m2cgen}.

\section{Dataset Manipulation}
\subsection{Updating the Dataset}
Upon inspection of the \texttt{combined_matches_games_ids} table discussed in \autoref{chap:req_analysis}, it became apparent that during the addition of 2025 VCT statistics folder by the author, the \texttt{all_ids} folder had failed to be updated to reflect any new data. Thus to maintain relational integrity, 2025 data was added to the master ID tables. Firstly, new player records and their associated identifiers were extracted from the 2025 dataset and appended to the master player IDs table. To ensure uniqueness, this operation was followed by a de-duplication step, which identified and removed redundant entries while preserving new additions from 2025.
\begin{lstlisting}[style=code, caption={Introducing new 2025 VCT data into the master ID tables.}]
path = Path(__file__).parent.parent / "dataset"
path_2025 = path / "vct_2025" / "ids"
new_path = path.parent / "new_data"

# BLOCK Of CODE FOR UPDATING THE all_players_ids.csv
all_players_ids = pd.read_csv(path / "all_ids" / "all_players_ids.csv")
new_player_ids = pd.read_csv(path_2025 / "players_ids.csv")

combined_player_ids = pd.concat([all_players_ids, new_player_ids]).drop_duplicates()
combined_player_ids.to_csv(new_path / "combined_player_ids.csv", index=False)
\end{lstlisting}

Following the update to the player table, an identical approach was applied to the remaining ID-bearing tables. Most importantly, the IDs for teams, matches, and games were each subjected to the same process. By executing the equivalent concatenation and de-duplication operations across these tables, the system was updated to ensure that all relational mapping files were synchronised with the 2025 dataset. The complete code listing for this process is displayed in \autoref{lst:all_matchesCreation}.

\subsection{Merge IDs}
As explained in \autoref{sub:key-tables}, the primary base for the dataset is the \texttt{map\_scores.csv} file, To create a longitudinal dataset, each annual \texttt{map\_scores} file was appended to an `all\_matches' master table, as seen in \autoref{lst:all_matchesCreation}. The overview and eco_stats files were also subjected to the same process. Once again, it it worth noting that the complete schemas for each table are defined in \autoref{fig:tableSchema}.

\begin{lstlisting}[style=code, caption={Consolidating all five years worth of statistics for maps_scores, overview, and eco_stats}, label={lst:all_matchesCreation}]
all_maps: list[pd.DataFrame] = []
all_overview: list[pd.DataFrame] = []
all_eco: list[pd.DataFrame] = []
for year in [2021, 2022, 2023, 2024, 2025]:
    matches = pd.read_csv(dataset / f'vct_{year}' / 'matches' / 'maps_scores.csv')
    matches["Year"] = year
    all_maps.append(matches)
    # ... same for all_overview and all_eco

all_matches: pd.DataFrame = pd.concat(all_maps, ignore_index=True)
df_overview = pd.concat(all_overview, ignore_index=True)
df_eco = pd.concat(all_eco, ignore_index=True)
\end{lstlisting}

To introduce unique identifiers to the data, the \texttt{combined\_matches\_games\_ids.csv} was utilised as a secondary source. However, merging these files posed a challenge. The combination of \texttt{Tournament}, \texttt{Stage}, \texttt{Match Type}, \texttt{Match Name}, and \texttt{Map} was not strictly unique in scenarios where the same map was played multiple times within a single series. To resolve this, a \texttt{Map\_Rank} column was introduced. By applying a cumcount() function grouped by the aforementioned fields, the system assigned a sequential rank to each occurrence, creating a unique composite key for merging:

\begin{lstlisting}[style=code, caption={Utilising the date ordering of identical records to assign a unique identifier. This identifier is used as a composite key for merging with the IDs table}]
# Unique identifier for matches played on the same map
all_matches['Map_Rank'] = all_matches.groupby(merge_keys).cumcount()
match_ids['Map_Rank'] = match_ids.groupby(merge_keys).cumcount()

all_matches = all_matches.merge(
    match_ids[merge_keys + ['Map_Rank', 'Game ID']], 
    how="left"
)

all_matches = all_matches.drop(columns=['Map_Rank'])
\end{lstlisting}

With the matches identified, the pipeline integrates team identifiers to facilitate the rolling statistics calculations described in \autoref{sub:featureStorage}. Using \texttt{combined\_team\_ids.csv}, the pipeline maps text team names to standardised database IDs. This involves a two-stage join to attribute distinct IDs to both Team A and Team B:

\begin{lstlisting}[style=code, caption={Merging the team IDs into all_matches for Team A and Team B}]
# Merge the Team IDs into the table
team_ids = pd.read_csv(dataset / "all_ids" / "combined_team_ids.csv")

# Merge for Team A
all_matches = all_matches.merge(team_ids, how='left', left_on="Team A", right_on="Team")
all_matches = all_matches.rename(columns={"Team ID": "Team A ID"}).drop(columns=['Team'])

# Merge for Team B
all_matches = all_matches.merge(team_ids, how='left', left_on="Team B", right_on="Team")
all_matches = all_matches.rename(columns={"Team ID": "Team B ID"}).drop(columns=['Team'])

all_matches = all_matches.astype({col: 'Int64' for col in all_matches.select_dtypes('float64').columns})
\end{lstlisting}

The culmination of this process is the consolidated `all_matches' master table. By establishing a row per match and embedding unique identifiers for both matches and teams, this table serves as the definitive fact base for the system. This structured integration not only resolves the ambiguity surrounding duplicate map instances but also provides a stable relational foundation. Consequently, the table is now prepared to be further enriched with new predictive features.

\subsection{Feature Derivation}
\label{sub:featureDerivation}
With the `all_matches' master table established, the focus shifted to implementing the predictive features defined in the feature summary \autoref{tab:feature_summary}. Beyond standard performance indicators, it was determined that player-level and economic metrics were essential for improving the model's predictive accuracy. Consequently, the feature derivation pipeline was structured into four distinct categories:
\begin{enumerate}
    \item \textbf{Head to Head Performance}
    \item \textbf{Individual Team Performance} 
    \item \textbf{Player-level Performance}
    \item \textbf{Round-type Outcomes}
\end{enumerate}

The head-to-head (H2H) category consists of only one feature: the head-to-head win differential. This feature, ranging between -1 and 1, quantifies the historical advantage between specific team combinations. To ensure consistency, a unique identifier is generated for each combination of teams by concatenating their lexicographically sorted \texttt{Team ID}s:
\begin{lstlisting}[style=code, caption={Unique team-combination key created}]
# Create a unique key for the two teams (alphabetical)
matches['Pair'] = matches.apply(lambda x: "_".join(sorted([str(x['Team A ID']), str(x['Team B ID'])])), axis=1)
\end{lstlisting}

The win rate for the `left' team in this pair is then calculated, and mapped to \texttt{Team A}'s perspective:
\begin{lstlisting}[style=code, caption={Calculate all time mean for left team win rate, mapping the value to Team A's perspective}]
matches['L_Won'] = matches.apply(
    lambda x: x['Team A Won'] if str(x['Team A ID']) < str(x['Team B ID']) else (1 - x['Team A Won']), axis=1
)

# Expanding mean (all time history)
matches['H2H_Base'] = matches.groupby('Pair')['L_Won'].transform(lambda x: x.shift(1).expanding().mean())

# Map to Team A perspective
matches['Team_A_H2H'] = matches.apply(
    lambda x: x['H2H_Base'] if str(x['Team A ID']) < str(x['Team B ID']) else (1 - x['H2H_Base']), axis=1
)
\end{lstlisting}

Finally, it is transformed into an unbiased differential feature scaled between -1 and 1, where -1 represents 100\% win rate for \texttt{Team B}, and 1 represents 100\% win rate for \texttt{Team A}:
\begin{lstlisting}[style=code, caption={Transform Team A specific metric into a differential}]
matches['H2H_Win_Diff'] = (2 * matches['Team_A_H2H'].fillna(0.5)) - 1
\end{lstlisting}

To compute team-based performance, the pipeline generates a specialised \texttt{hist} DataFrame containing two rows per match---one for each team. This allows for the calculation of performance indicators, including overall win rates, map-specific win rates, round differentials, and side-specific (Attacker/Defender) win rates. These features are calculated using an exponentially weighted moving average (EWMA) with a span of 15 matches, which prioritises recent performance while smoothing out any anomalies.
\begin{lstlisting}[style=code, caption={Calculating the rolling average for each team}]
def get_rolling(df: pd.DataFrame, group_cols, target_col, span=15):
    return df.groupby(group_cols)[target_col].transform(lambda x: x.shift(1).ewm(span=span, adjust=False).mean())
hist['Roll_Form'] = get_rolling(hist, 'Team ID', 'Won')
hist['Roll_Map'] = get_rolling(hist, ['Team ID', 'Map'], 'Won')
hist['Roll_RD'] = get_rolling(hist, 'Team ID', 'RD')
hist['Roll_Atk_Map'] = get_rolling(hist, ['Team ID', 'Map'], 'Atk_W')
hist['Roll_Def_Map'] = get_rolling(hist, ['Team ID', 'Map'], 'Def_W')
\end{lstlisting}

These absolute values are subsequently converted into differential features, representing the competitive gap between the two contesting teams.

\begin{lstlisting}[style=code, caption={Convert team specific features into differential features}]
for side in ['A', 'B']:
    hist_subset = hist[['Game ID', 'Team ID', 'Roll_Form', 'Roll_Map', 'Roll_RD', 'Roll_Atk_Map', 'Roll_Def_Map']]
    matches = matches.merge(hist_subset, left_on=['Game ID', f'Team {side} ID'], right_on=['Game ID', 'Team ID'], how='left')
    matches = matches.rename(columns={
        'Roll_Form': f'T{side}_W', 'Roll_Map': f'T{side}_M', 'Roll_RD': f'T{side}_RD',
        'Roll_Atk_Map': f'T{side}_Atk_M', 'Roll_Def_Map': f'T{side}_Def_M'
    }).drop(columns='Team ID')
matches['Form_Win_Rate_Diff'] = matches['TA_W'] - matches['TB_W']
matches['Map_Win_Rate_Diff'] = matches['TA_M'] - matches['TB_M']
matches['Round_Diff'] = matches['TA_RD'] - matches['TB_RD']
matches['Map_Atk_Diff'] = matches['TA_Atk_M'] - matches['TB_Atk_M']
matches['Map_Def_Diff'] = matches['TA_Def_M'] - matches['TB_Def_M']
\end{lstlisting}

Finally, the player and economic tables provide a granular view of team proficiency. For player stats, the system aggregates \texttt{ACS}, \texttt{KAST}, and \texttt{First Bloods} for each individual on the team, calculating the team's match average. Similarly, economic metrics are derived from round-by-round data, tracking pistol round and low-buy success. As with the team metrics, these aggregates are passed through the same EWMA pipeline and converted into differential features, resulting in a robust, multi-dimensional dataset for predictive inference. The final features comprising the dataset can be seen in the table below:

\section{Logistic Regression Model}
Prior to the addition of the player-level and economic features discussed in the previous section, a baseline Logistic Regression model was developed using the initial feature set defined in \autoref{tab:feature_summary}. The primary objective of this stage was to establish a proof-of-concept for the end-to-end system, ensuring that the data pipeline could successfully feed a model capable of generating real-time predictions.

The dataset, at this stage consisting solely of team performance metrics, was partitioned using a standard 70/30 train-test split and fitted using the \texttt{scikit-learn} implementation of Logistic Regression. The initial model achieved an accuracy of 53\%. While this performance represents only a modest improvement over random baseline guessing, it provided a functionally complete model capable of being exported and integrated into the Alexa Skill for system testing. Before further model optimisation took place, the interaction model and the Lambda Function were established to facilitate a realistic test of the project. Subsequently, the model was re-developed to achieve a higher accuracy.

\section{Gradient-Boosted Tree Model}

To produce a model with greater predictive accuracy, it became necessary to address the non-linear relationships inherent within the esports dataset. While linear models process features in isolation, a tree-based approach can understand complex feature interactions and non-linear thresholds (for instance, recognising that a high combat score is irrelevant if a team's economy conversion rate falls below a certain percentage). To capture these nuances, gradient-boosted decision trees were selected as the primary architecture for the final model.

\subsection{scikit-learn and Deployment Constraints}
The initial iteration of the gradient-boosted model was developed using the \texttt{scikit-learn} library's \texttt{GradientBoostingClassifier}. While the model trained successfully and demonstrated promising predictive capabilities locally, a critical infrastructure limitation was encountered during deployment. 

The Alexa Skill's backend is hosted on AWS Lambda, which enforces a strict 250 MB unzipped deployment package size limit. Bundling the \texttt{scikit-learn} library, alongside its heavy mathematical dependencies (\texttt{NumPy} and \texttt{SciPy}) and the serialised \texttt{joblib} model file, comfortably exceeded this quota, resulting in AWS Lambda refusing the deployment. This bottleneck caused the exploration of alternative deployment avenues that did not rely on bulky external libraries.

\subsection{XGBoost and the m2cgen Library}
To bypass the Lambda size constraints, \texttt{m2cgen} (Model to Code Generator) was identified as an essential tool. \texttt{m2cgen} translates trained machine learning models into native, dependency free Python code---effectively converting a complex forest of decision trees into a single script of nested \texttt{if/else} statements. This eliminates the need to install any machine learning libraries on the AWS server.

Initially, XGBoost was selected as the candidate algorithm, given its strong reputation in classification tasks (as discussed in \autoref{chap:technology survey}). However, upon attempting to compile the trained model, it was discovered that the specific implementation of XGBoost was incompatible with \texttt{m2cgen} at the required complexity. Further research into potential fixes for this issue only yielded confirmations of the incompatibility, alongside suggestions that a more lightweight framework, LightGBM, may be the answer.

\subsection{LightGBM Implementation}
LightGBM is Microsoft's open-source gradient-boosting algorithm. Unlike traditional boosting algorithms that grow trees level-wise (depth-first), LightGBM employs a leaf-wise (best-first) growth strategy. It chooses to grow the leaf with the maximum delta loss, which often results in better accuracy and faster training times. Crucially for this project, LightGBM is highly memory efficient, making the resulting \texttt{m2cgen} export much more manageable for the Lambda execution environment.

Because leaf-wise growth is susceptible to overfitting on smaller datasets, the model was heavily constrained via hyperparameter tuning to ensure it generalised effectively to unseen matches. The final configuration used to train the model is detailed in \autoref{tab:lightgbm_hyperparameters}.

\subsubsection{Feature Selection}
LightGBM natively calculates feature importances, providing transparency into the model's decision making process. Analysis of these importances revealed multicollinearity and redundancy within the dataset. Specifically, \texttt{Form\_Win\_Rate\_Diff}, \texttt{Pistol\_Diff}, \texttt{Map\_Win\_Rat\-e\_Diff}, and \texttt{KAST\_Diff} were identified as mathematically overlapping with more prominent features. 

These variables were subsequently dropped from the training set, streamlining the model and forcing it to focus on non-redundant features. The final feature importances (\autoref{tab:feature_importances}) highlighted a strong preference for raw score and economic efficiency.

\subsection{Testing the Model}
In accordance with the evaluation strategies established in \autoref{chap:req_analysis}, the LightGBM model was tuned and tested against a 70\% training set, a 20\% hold-out testing set, and a 10\% final validation set. The model was evaluated against the testing set upon each hyperparameter tweak, with the goal of reaching the highest accuracy possible. The purpose of the validation set was to provide a final evaluation of the model on completely unseen data, ensuring that it has not been overfitted to the testing set.

\begin{lstlisting}[style=code, caption={Training the final LightGBM model and exporting it to Python using m2cgen.}]
import lightgbm as lgb
import m2cgen as m2c

# Training the LightGBM model
model = lgb.LGBMClassifier(
    n_estimators = 150,
    max_depth = 4,
    num_leaves = 15,
    learning_rate = 0.05,
    colsample_bytree = 0.8,
    subsample = 0.8,
    random_state=42
).fit(X_train, y_train)
\end{lstlisting}

\section{Interaction Model}
The skill, invoked by the name `valorant predictor', is built upon a structured interaction model designed to enable accurate entity resolution and conversational flow. The interaction model was developed within the Alexa developer console, a web interface for managing owned Alexa skills.

\subsection{Custom Slot Type: team}
A custom slot type named \texttt{team} was defined within the interaction model, containing a comprehensive mapping of team names to their respective database IDs. This provides AVS with the data needed to identify that a user's phonetic request matches an existing ID.

Additionally, synonyms---covering common mispronunciations and alternative spellings---for potentially ambiguous team names were generated with the use of Google Gemini. Due to the volume of teams (around 4000) it was decided that this task was well suited for the tool of generative AI. The usage of gen AI was in accordance with the university's guidelines, and is described in \autoref{app:genAI} as required by the University. These synonyms significantly increase the likelihood of successful entity resolution, reducing the chance of a user's valid request being misunderstood due to the team name used.

\section{Lambda Function}
The Lambda Function is a Python back-end hosted on AWS Lambda.
\subsection{MatchPredictionIntent Handler}

To give the \texttt{MatchPredictionIntent} specific executable logic, a custom handler class was created following the design pattern established in \autoref{sub:handlerDesignpattern}. This handler carries out a multi-tiered process encompassing user input validation, data retrieval, feature calculation, and model execution.

The first stage of the handler relies on the \texttt{get\_resolved\_value} function, which validates the user's spoken team names against the skill's interaction model. If the required slot is completely missing, the function returns \texttt{None}. If the spoken word is heard but does not map to a known entity in the list of slot values, it returns the spoken value marked as unresolved. However, if a successful match is made---indicated by the \texttt{ER\_SUCCESS\_MATCH} status code---it extracts and returns the official team name and its corresponding unique ID.

\begin{lstlisting}[style=code, caption={Helper function to resolve and validate user slot inputs.}]
def get_resolved_value(slot):
    # Check if the slot is completely missing or empty
    if not slot or not slot.value:
        return None 

    # Check if the slot successfully resolved to a team ID
    if slot.resolutions and slot.resolutions.resolutions_per_authority:
        for authority in slot.resolutions.resolutions_per_authority:
            if authority.status.code.value == "ER_SUCCESS_MATCH":
                return {
                    "id": authority.values[0].value.id,
                    "name": authority.values[0].value.name
                }
                
    # The slot has a spoken value, but it didn't match an ID
    return {
        "id": None, 
        "name": slot.value, 
        "unresolved": True
    }
\end{lstlisting}

Within the handler's \texttt{handle} method, conversational dialogue is managed dynamically based on the results of this validation. If a team variable returns as \texttt{None}, the skill acknowledges the missed input and prompts the user to repeat the team name. If the variable is marked as unresolved, the skill acknowledges the heard name but explains that the team is not currently in the database. This provides a graceful fallback rather than a system crash.

Once the slots are successfully resolved, the handler attempts to load the corresponding statistics for those teams. The data is retrieved from a pre-loaded dictionary, generated by the \texttt{load\_stats} function, which uses the resolved team IDs as primary keys to access recent performance metrics. These metrics are stored within the \texttt{team_stats} CSV file, created alongside the final feature set as described at the end of \autoref{sub:featureDerivation}. A final validation check ensures that the required values are returned; if the lookup is empty, the skill informs the user that whilst the team is recognised, their statistical data is unavailable at the moment.

\begin{lstlisting}[style=code, caption={Function to load team statistics into memory using the Team ID as a key.}]
def load_stats():
    team_stats = {}
    file_path = os.path.join(os.path.dirname(__file__), 'resources', 'team_stats.csv')
    
    with open(file_path, mode='r', encoding='utf-8') as f:
        reader = csv.DictReader(f)
        for row in reader:
            # Map the ID to the rest of the data
            team_stats[row['Team_ID']] = {
                'RD': float(row['RD']),
                'Atk_M': float(row['Atk_M']),
                'Def_M': float(row['Def_M']),
                'ACS': float(row['ACS']),
                'FB': float(row['FB']),
                'Eco': float(row['Eco'])
            }

    return team_stats
\end{lstlisting}

If all checks pass, the handler delegates the mathematical processing to the \texttt{pred\-ict\_match\_winner} method. By enforcing that the team with the lower numerical ID is always treated as the primary team, the system successfully removes any prediction bias that could arise from the arbitrary order in which the user spoke the team names. 

The method then calculates the differential features between the two teams and passes them into the exported LightGBM \texttt{score} function. The resulting probabilities are evaluated to determine the predicted winner and the model's confidence percentage.

\begin{lstlisting}[style=code, caption={Method to standardise input order, calculate feature differentials, and execute the prediction model.}]
def predict_match_winner(self, team_a, team_b, data_a, data_b):
    if team_a['id'] < team_b['id']:
        team_one = team_a
        team_two = team_b
        data_one = data_a
        data_two = data_b
    else:
        team_one = team_b
        team_two = team_a
        data_one = data_b
        data_two = data_a

    H2H_Win_Diff = 0.0
    Round_Diff = data_one['RD'] - data_two['RD']
    Map_Atk_Diff = data_one['Atk_M'] - data_two['Atk_M']
    Map_Def_Diff = data_one['Def_M'] - data_two['Def_M']
    ACS_Diff = data_one['ACS'] - data_two['ACS']
    FB_Diff = data_one['FB'] - data_two['FB']
    Eco_Diff = data_one['Eco'] - data_two['Eco']

    features = [
        H2H_Win_Diff,
        Round_Diff,
        Map_Atk_Diff,
        Map_Def_Diff,
        ACS_Diff,
        FB_Diff,
        Eco_Diff
    ]

    prediction_probs = score(features)
    prob_team_one = prediction_probs[1]

    if prob_team_one > 0.5:
        winner_name = team_one['name']
        confidence = prob_team_one * 100
    else:
        winner_name = team_two['name']
        confidence = (1.0 - prob_team_one) * 100
    return winner_name, confidence
\end{lstlisting}

Subsequently, the Lambda function handles the wording and formatting of the spoken response. It constructs a natural language string containing the predicted winner and the confidence percentage, and speaks this result back to the user. Finally, the handler updates the session's \texttt{last_action} attribute to `prediction_complete', and keeps the session open to allow for subsequent match predictions.

\subsection{Built-in Handlers}

To manage the natural flow of conversation, the skill utilises the built-in intents \texttt{AMAZON.YesIn\-tent} and \texttt{AMAZON.NoIntent}. These handlers are primarily designed to respond to the prompt issued at the end of the \texttt{MatchPredictionIntent}, where the user is asked if they would like to make another prediction.

To achieve contextual awareness, the skill employs session attributes to track the state of the dialogue. As established in the previous subsection, when a prediction successfully completes, a \texttt{last\_action} attribute is temporarily saved to the session and flagged as `prediction\_complete'. The built-in handlers retrieve this attribute to understand the context of the user's affirmative or negative response.

If the \texttt{YesIntentHandler} detects this flag, it clears the session attribute to reset the state and prompts the user to provide two new teams, smoothly initiating a new prediction loop. Conversely, if the user declines by triggering the \texttt{NoIntentHandler}, the skill clears the attribute, delivers a polite farewell message, and explicitly terminates the session using the \texttt{set\_should\_end\_session(True)} directive.

Furthermore, should a user randomly say `Yes' or `No' out of context (i.e., when the \texttt{last\_action} flag is \texttt{None}), the handlers acknowledge the confusion and guide the user back to the skill's core functionality rather than silently failing or closing.

\begin{lstlisting}[style=code, caption={Implementation of the Yes and No intent handlers using session attributes for contextual routing.}]
class YesIntentHandler(AbstractRequestHandler):
    """Handler for Yes Intent."""
    def can_handle(self, handler_input):
        # type: (HandlerInput) -> bool
        return ask_utils.is_intent_name("AMAZON.YesIntent")(handler_input)

    def handle(self, handler_input):
        # type: (HandlerInput) -> Response
        last_action = handler_input.attributes_manager.session_attributes.get("last_action")

        if last_action == "prediction_complete":
            handler_input.attributes_manager.session_attributes["last_action"] = None
            speak_output = "Great! Which two teams are playing this time?"
            reprompt = "Tell me the names of the two teams."
        else:
            speak_output = "I'm not sure what you're saying yes to. What can I help with?"
            reprompt = "You can ask for a match prediction."
        
        return (
            handler_input.response_builder
                .speak(speak_output)
                .ask(reprompt)
                .response
        )
    
class NoIntentHandler(AbstractRequestHandler):
    """Handler for No Intent."""
    def can_handle(self, handler_input):
        # type: (HandlerInput) -> bool
        return ask_utils.is_intent_name("AMAZON.NoIntent")(handler_input)

    def handle(self, handler_input):
        # type: (HandlerInput) -> Response
        last_action = handler_input.attributes_manager.session_attributes.get("last_action")

        if last_action == "prediction_complete":
            handler_input.attributes_manager.session_attributes["last_action"] = None
            speak_output = "No problem. Good luck with the matches! Goodbye."
            return (
                handler_input.response_builder
                    .speak(speak_output)
                    .set_should_end_session(True)
                    .response
            )
        else:
            speak_output = "I'm not sure what you're saying no to. You can ask me to predict a match, or say help."
            return (
                handler_input.response_builder
                    .speak(speak_output)
                    .ask("How can I help you?") # Keep session alive
                    .response
            )
\end{lstlisting}
